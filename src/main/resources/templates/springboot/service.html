Service 레이어

비즈니스 로직을 처리하는 Service 계층의 어노테이션을 학습합니다

예제: OrderService 

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)  // 기본: 읽기 전용
public class OrderService {

    private final OrderRepository orderRepository;
    private final OrderItemRepository orderItemRepository;

    // 1. 전체 조회 (읽기 전용 트랜잭션)
    public List<Order> findAll() {
        return orderRepository.findAll();
    }

    // 2. 단건 조회
    public Order findById(Long id) {
        return orderRepository.findById(id)
            .orElseThrow(() -> new IllegalArgumentException("주문을 찾을 수 없습니다"));
    }

    // 3. 생성 (쓰기 트랜잭션)
    @Transactional  // readOnly = false (기본값)
    public Order create(OrderRequest request) {
        // 1. 주문 생성
        Order order = Order.builder()
            .customerName(request.getCustomerName())
            .orderDate(LocalDateTime.now())
            .status(OrderStatus.PENDING)
            .build();

        // 2. 주문 아이템 추가
        for (OrderItemRequest itemReq : request.getItems()) {
            OrderItem item = OrderItem.builder()
                .productName(itemReq.getProductName())
                .quantity(itemReq.getQuantity())
                .price(itemReq.getPrice())
                .build();
            order.addItem(item);
        }

        // 3. 저장 (cascade로 자동 저장됨)
        return orderRepository.save(order);
    }

    // 4. 수정
    @Transactional
    public Order update(Long id, OrderRequest request) {
        Order order = findById(id);
        order.setCustomerName(request.getCustomerName());
        order.setStatus(request.getStatus());
        return order; // 변경 감지로 자동 UPDATE
    }

    // 5. 삭제
    @Transactional
    public void delete(Long id) {
        Order order = findById(id);
        orderRepository.delete(order);
    }

    // 6. 검색
    public List<Order> findByCustomerName(String name) {
        return orderRepository.findByCustomerNameContaining(name);
    }
}

Service 어노테이션 정리

그룹 1 기본 Service 어노테이션

어노테이션 설명 예시
@Service 서비스 계층 컴포넌트 선언
Spring Bean으로 자동 등록		 @Service public class OrderService { }
@RequiredArgsConstructor final 필드 생성자 주입
Lombok, 의존성 주입 편리		 @RequiredArgsConstructor
@Autowired 의존성 자동 주입
생성자 주입 권장 (생략 가능)		 @Autowired private OrderRepository repo;

그룹 2 트랜잭션 관리 어노테이션

어노테이션 설명 예시
@Transactional 트랜잭션 범위 설정
클래스/메서드 레벨 모두 가능		 @Transactional public void save() { }
readOnly = true 읽기 전용 트랜잭션
조회 성능 최적화, 변경 방지		 @Transactional(readOnly = true)
readOnly = false 쓰기 트랜잭션 (기본값)
INSERT, UPDATE, DELETE		 @Transactional (기본값)
propagation 트랜잭션 전파 속성
REQUIRED, REQUIRES_NEW 등		 propagation = Propagation.REQUIRES_NEW
isolation 트랜잭션 격리 수준
READ_COMMITTED, REPEATABLE_READ 등		 isolation = Isolation.READ_COMMITTED
rollbackFor 롤백 예외 지정
특정 예외 발생 시 롤백		 rollbackFor = Exception.class
timeout 트랜잭션 타임아웃 (초)
지정 시간 초과 시 롤백		 timeout = 10 (10초)

그룹 3 캐싱 어노테이션 (선택)

어노테이션 설명 예시
@Cacheable 메서드 결과를 캐시에 저장
같은 파라미터면 캐시 반환		 @Cacheable("orders")
@CacheEvict 캐시 삭제
데이터 변경 시 캐시 무효화		 @CacheEvict(value = "orders", allEntries = true)
@CachePut 캐시 갱신
메서드 실행 후 결과를 캐시에 저장		 @CachePut(value = "orders", key = "#id")

@Transactional 심화

트랜잭션 전파 속성 (Propagation)

속성 설명
REQUIRED (기본) 부모 트랜잭션이 있으면 참여, 없으면 새로 생성
가장 많이 사용, 일반적인 상황
REQUIRES_NEW 항상 새로운 트랜잭션 생성, 부모는 일시 정지
독립적인 트랜잭션 필요 시 (로그 저장 등)
SUPPORTS 부모 트랜잭션이 있으면 참여, 없어도 OK
트랜잭션 없이도 실행 가능
MANDATORY 부모 트랜잭션 필수, 없으면 예외 발생
반드시 트랜잭션 내에서 호출되어야 함
NOT_SUPPORTED 트랜잭션 없이 실행, 부모가 있으면 일시 정지
트랜잭션이 불필요한 작업
NEVER 트랜잭션 없이 실행, 부모가 있으면 예외 발생
트랜잭션 금지

실무 예제

@Service
public class OrderService {

    // 일반적인 경우: REQUIRED (기본값)
    @Transactional
    public void createOrder() {
        orderRepository.save(order);
        logService.saveLog("주문 생성"); // 같은 트랜잭션
    }

    // 독립적인 트랜잭션: REQUIRES_NEW
    @Transactional
    public void createOrderWithLog() {
        orderRepository.save(order);
        logService.saveLogIndependent(); // 별도 트랜잭션
    }
}

@Service
public class LogService {

    // 주문이 실패해도 로그는 저장됨
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveLogIndependent() {
        logRepository.save(log);
    }
}

실무 팁

권장사항

  • • 클래스에 readOnly = true: 조회 메서드가 많을 때
  • • 메서드에 @Transactional: 변경 메서드만 오버라이드
  • • 생성자 주입 사용: @RequiredArgsConstructor 활용
  • • Service는 얇게: 복잡한 로직은 Entity에

주의사항

  • • private 메서드: @Transactional 동작 안 함
  • • self-invocation: 같은 클래스 메서드 호출 시 AOP 미적용
  • • 예외 처리: RuntimeException만 자동 롤백
  • • 트랜잭션 크기: 너무 크면 성능 저하

흔한 실수: self-invocation 

@Service
public class OrderService {

    // ❌ 동작 안 함: 같은 클래스 내부 호출
    public void processOrder() {
        this.createOrder(); // @Transactional 무시됨!
    }

    @Transactional
    public void createOrder() {
        orderRepository.save(order);
    }
}

// ✅ 해결 방법: 별도 Service로 분리
@Service
public class OrderProcessService {
    private final OrderService orderService;

    public void processOrder() {
        orderService.createOrder(); // 정상 동작
    }
}
