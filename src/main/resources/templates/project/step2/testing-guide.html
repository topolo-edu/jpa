무엇을 테스트해야 하나요? (우선순위)

1순위: 비즈니스 로직 (엔티티 메서드)

필수 (3개 이상)

Service가 아닌 Entity에 있는 핵심 로직을 테스트

예시:

  • 정원 초과 시 수강신청 실패
  • 중복 수강신청 방지
  • 승인된 수강신청은 취소 불가
  • 강의 삭제 시 커리큘럼 함께 삭제 (Cascade)

2순위: 주요 API (통합 테스트)

권장 (2~3개)

모든 API 아니고, 핵심 API만 테스트

예시:

  • POST /api/enrollments (수강신청 성공/실패)
  • GET /api/courses/1 (N+1 발생 안 하는지)
  • PATCH /api/enrollments/1/approve (비관적 락 동작)

3순위: 복잡한 쿼리 (Repository)

선택

QueryDSL로 작성한 복잡한 통계 쿼리만

예시:

  • 강의별 수강생 통계 (QueryDSL)
  • 월별 수강신청 집계

복붙 가능한 코드 템플릿

1순위 단위 테스트 - 비즈니스 로직 

@Test
@DisplayName("정원 초과 시 수강신청 실패")
void enrollFail_WhenExceedMaxStudents() {
    // given (준비)
    Course course = Course.builder()
        .name("JPA 마스터")
        .maxStudents(30)
        .build();

    // 30명 등록 (정원 채움)
    for (int i = 0; i < 30; i++) {
        User user = new User("user" + i);
        course.enroll(user); // 편의 메서드
    }

    User lateUser = new User("늦은사람");

    // when & then (실행 & 검증)
    assertThatThrownBy(() -> course.enroll(lateUser))
        .isInstanceOf(IllegalStateException.class)
        .hasMessage("정원 초과");
}

@Test
@DisplayName("중복 수강신청 방지")
void enrollFail_WhenDuplicate() {
    // given
    Course course = new Course("JPA 마스터");
    User user = new User("홍길동");
    course.enroll(user); // 1차 신청

    // when & then
    assertThatThrownBy(() -> course.enroll(user))
        .isInstanceOf(IllegalStateException.class)
        .hasMessage("이미 수강신청한 강의입니다");
}
핵심: Service 아니고 Course.enroll(user) 같은 엔티티 메서드를 테스트!

2순위 통합 테스트 - API 

@SpringBootTest
@AutoConfigureMockMvc
@Transactional
class EnrollmentApiTest {

    @Autowired private MockMvc mockMvc;
    @Autowired private ObjectMapper objectMapper;

    @Test
    @DisplayName("수강신청 성공")
    void enroll_Success() throws Exception {
        // given
        EnrollRequest request = new EnrollRequest(1L, 1L);

        // when & then
        mockMvc.perform(post("/api/enrollments")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.status").value("PENDING"));
    }

    @Test
    @DisplayName("정원 초과 시 400 에러")
    void enroll_Fail_WhenExceed() throws Exception {
        // given: 정원 30명인 강의에 30명 등록 후
        EnrollRequest request = new EnrollRequest(1L, 31L);

        // when & then
        mockMvc.perform(post("/api/enrollments")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.message").value("정원 초과"));
    }
}

자주 하는 실수

❌ 하지 말아야 할 것

  • • Service의 모든 메서드 테스트
  • • Repository CRUD 테스트 (JPA가 알아서 함)
  • • Getter/Setter 테스트
  • • 테스트를 위한 테스트 (의미 없는 테스트)
  • • 80% 커버리지 목표 (7일 프로젝트엔 비현실적)

✅ 집중해야 할 것

  • • 엔티티 비즈니스 로직 (정원 체크 등)
  • • 주요 API 2~3개 (수강신청, 조회)
  • • N+1 해결 검증 (쿼리 개수 확인)
  • • 예외 처리 (정원 초과 시 에러)
  • • 발표 자료 활용 (품질 어필)

성능 테스트 (nGrinder)

nGrinder란?

네이버에서 만든 부하 테스트 도구
동시 접속자 100명, 1000명을 시뮬레이션해서 서버가 버티는지 확인

예시: "수강신청 API에 동시 100명 요청 → TPS 150, 평균 응답 시간 45ms"

1단계: nGrinder 설치 (Docker)

# nGrinder Controller 실행

docker run -d -p 8300:80 -p 16001:16001 -p 12000-12009:12000-12009 ngrinder/controller

# 브라우저에서 접속

http://localhost:8300

기본 계정: admin / admin

2단계: 테스트 스크립트 작성 

// Script → Create → Groovy

import static net.grinder.script.Grinder.grinder
import HTTPRequest

class TestRunner {
    private HTTPRequest request

    @BeforeThread
    void beforeThread() {
        request = new HTTPRequest()
    }

    @Test
    void test() {
        // GET 요청 예시
        request.GET("http://localhost:8080/api/courses/1")

        // POST 요청 예시
        def body = """{"courseNo":1,"userNo":1}"""
        def headers = [("Content-Type"): "application/json"]
        request.POST("http://localhost:8080/api/enrollments", body, headers)
    }
}

3단계: 테스트 실행

설정 값

  • Vuser (가상 사용자): 100명
  • Duration: 1분
  • Script: 위에서 작성한 스크립트 선택

확인할 지표

  • TPS: 초당 처리 요청 수 (높을수록 좋음)
  • Mean Test Time: 평균 응답 시간 (낮을수록 좋음)
  • Errors: 에러 개수 (0이어야 함)

성능 테스트 활용 팁

Before/After 비교

1. N+1 문제 있을 때 테스트 실행 → TPS 50
2. Fetch Join 적용 후 다시 실행 → TPS 200
3. 발표 자료: "성능 4배 개선"

Actuator와 함께 사용

nGrinder 실행 중 /actuator/metrics/system.cpu.usage 확인
CPU 사용률이 100%면 서버 증설 필요

비관적 락 테스트

동시 100명이 같은 강의 수강신청 → 비관적 락으로 순차 처리
에러 없이 30명만 성공, 70명 실패 확인
