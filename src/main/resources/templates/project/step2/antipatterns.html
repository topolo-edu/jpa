Before/After로 보는 코드 개선 사례

목록으로

안티패턴 1: 잘못된 타이밍의 currentStudents 증가

문제점

  • 증가 시점 오류: 수강신청 생성(PENDING) 시 currentStudents가 증가
  • 비즈니스 로직 불일치: 승인되지 않았는데 정원이 차버림
  • 데이터 불일치: 대기 중인 신청만 있어도 수강 마감 상태가 됨

❌ BEFORE (문제가 있는 코드)

Course.java

/** * 수강신청 추가 (편의 메서드) */ public void addEnrollment(Enrollment enrollment) { enrollments.add(enrollment); enrollment.setCourse(this); this.currentStudents++; // ❌ 문제: 수강신청 생성 시점에 증가! }

Enrollment.java

/** * 승인 */ public void approve() { this.status = EnrollmentStatus.APPROVED; // currentStudents는 변경 안 함 // ❌ 문제: 승인 시점에 증가해야 함! }

시나리오: 문제 발생

1. 강의 정원: 30명
2. 학생 A가 수강신청 (PENDING) → currentStudents = 1
3. 학생 B가 수강신청 (PENDING) → currentStudents = 2
   ...
30명이 모두 신청 (PENDING) → currentStudents = 30

❌ 결과: 아직 아무도 승인되지 않았는데 정원이 다 차버림!
❌ 다른 학생들은 수강신청조차 할 수 없음

✅ AFTER (개선된 코드)

Course.java

/** * 수강신청 추가 (편의 메서드) * - 양방향 관계 설정만 담당 * - currentStudents는 승인 시점에 증가 */ public void addEnrollment(Enrollment enrollment) { enrollments.add(enrollment); enrollment.setCourse(this); // currentStudents 증가 제거 // ✅ 개선: 양방향 관계만 설정 }

Enrollment.java

/** * 승인 * - 상태를 APPROVED로 변경 * - currentStudents 증가 */ public void approve() { if (this.status == EnrollmentStatus.APPROVED) { throw new IllegalStateException("이미 승인된 수강신청입니다."); } this.status = EnrollmentStatus.APPROVED; this.course.increaseCurrentStudents(); // ✅ 개선: 승인 시점에 증가! } /** * 취소 * - 대기 상태: soft delete만 수행 * - 승인 상태: soft delete + currentStudents 감소 */ public void cancel() { if (this.status == EnrollmentStatus.REJECTED) { throw new IllegalStateException("거절된 수강신청은 취소할 수 없습니다."); } // 승인된 상태였다면 currentStudents 감소 if (this.status == EnrollmentStatus.APPROVED) { this.course.decreaseCurrentStudents(); // ✅ 개선: 상태에 따라 감소 } this.delete(); }

시나리오: 정상 동작

1. 강의 정원: 30명
2. 학생 A가 수강신청 (PENDING) → currentStudents = 0
3. 학생 B가 수강신청 (PENDING) → currentStudents = 0
   ...
100명이 신청 (PENDING) → currentStudents = 0

4. 관리자가 30명 승인 → currentStudents = 30
5. 나머지 70명 거절

✅ 결과: 승인된 학생만 정원에 반영!
✅ 대기 중인 학생이 많아도 정원 확인에 영향 없음

핵심 교훈

  • ✅ 책임 분리: 편의 메서드는 양방향 관계만 담당, 비즈니스 로직은 엔티티 메서드가 담당
  • ✅ 상태와 데이터 일치: currentStudents는 APPROVED 상태의 수강생만 반영
  • ✅ 명확한 타이밍: 증가는 approve(), 감소는 cancel() (APPROVED인 경우만)

안티패턴 2: 배치 처리에서 전체 롤백

문제점

  • All or Nothing: 하나만 실패해도 전체가 롤백됨
  • 트랜잭션 범위 오류: 메서드 전체가 하나의 트랜잭션
  • 사용자 경험 저하: 99개 성공, 1개 실패 → 모두 실패로 표시

❌ BEFORE (문제가 있는 코드)

@Transactional // ❌ 문제: 메서드 전체가 하나의 트랜잭션! public BatchEnrollmentResponse batchProcessEnrollments(BatchEnrollmentRequest request) { List<Enrollment> enrollments = enrollmentRepository.findByIdsForBatchUpdate(...); List<EnrollmentProcessResult> results = new ArrayList<>(); for (Enrollment enrollment : enrollments) { try { processEnrollment(enrollment, ...); // ❌ 예외 발생 시 전체 롤백! results.add(success(...)); } catch (Exception e) { results.add(failure(...)); // catch해도 트랜잭션은 롤백됨 } } return BatchEnrollmentResponse.success(...); }

시나리오: 문제 발생

1. 100개의 수강신청 일괄 승인 요청
2. 1~99번: 정상 승인 처리
3. 100번: 예외 발생 (이미 승인됨)

❌ 결과: try-catch로 잡았지만...
❌ @Transactional이 메서드 전체에 있어서 전체 롤백!
❌ 1~99번까지 모두 되돌려짐
❌ 사용자는 "100개 중 0개 성공" 메시지를 받음

✅ AFTER (개선된 코드)

@Transactional(readOnly = true) // ✅ 개선: readOnly로 변경 public BatchEnrollmentResponse batchProcessEnrollments(BatchEnrollmentRequest request) { // 수강신청 ID 존재 여부 확인 (readOnly 트랜잭션에서) List<Enrollment> enrollments = enrollmentRepository.findByIdsForBatchUpdate(...); // 개별 처리 결과 수집 (각각 독립적인 트랜잭션) List<EnrollmentProcessResult> results = enrollments.stream() .map(enrollment -> processEnrollmentInNewTransaction( enrollment.getEnrollmentNo(), request.getAction(), request.getReason())) .collect(Collectors.toList()); // ✅ 각각 독립적 트랜잭션! return BatchEnrollmentResponse.success(...); } /** * 개별 수강신청을 새로운 트랜잭션에서 처리 * - Propagation.REQUIRES_NEW: 독립적인 트랜잭션 생성 * - 하나 실패해도 다른 트랜잭션에 영향 없음 */ @Transactional(propagation = Propagation.REQUIRES_NEW) // ✅ 핵심! public EnrollmentProcessResult processEnrollmentInNewTransaction( Long enrollmentNo, BatchAction action, String reason) { try { Enrollment enrollment = enrollmentRepository.findByIdForUpdate(enrollmentNo) .orElseThrow(...); processEnrollment(enrollment, action, reason); return success(...); // ✅ 이 트랜잭션만 커밋 } catch (Exception e) { return failure(...); // ✅ 이 트랜잭션만 롤백 } }

시나리오: 정상 동작

1. 100개의 수강신청 일괄 승인 요청
2. 각 수강신청이 독립적인 트랜잭션으로 처리
3. 1~99번: 정상 승인 → 각각 커밋됨
4. 100번: 예외 발생 → 이 트랜잭션만 롤백

✅ 결과: "100개 중 99개 성공, 1개 실패"
✅ 1~99번은 정상적으로 승인 유지
✅ 사용자는 어떤 항목이 실패했는지 명확히 알 수 있음

핵심 교훈

  • ✅ Propagation.REQUIRES_NEW: 새로운 트랜잭션 생성, 독립적으로 커밋/롤백
  • ✅ 부분 성공 허용: 배치 처리에서 일부 실패는 정상적인 시나리오
  • ✅ 명확한 피드백: 성공/실패 개수와 실패 사유를 각각 반환

안티패턴 3: 불명확한 에러 메시지 (UX 혼란)

문제점

  • 에러 원인 불명확: "강의를 찾을 수 없습니다" → 없는 건지? 정원 찬 건지?
  • Repository 책임 과다: 정원 확인까지 Repository가 담당
  • 디버깅 어려움: 로그만 봐서는 실제 원인 파악 힘듦

❌ BEFORE (문제가 있는 코드)

CourseRepository.java

@Lock(LockModeType.PESSIMISTIC_WRITE) @Query(""" SELECT c FROM Course c WHERE c.courseNo = :courseNo AND c.deleted = false AND c.currentStudents < c.maxStudents """) // ❌ 정원 확인을 쿼리에 포함 Course findAvailableByIdForEnrollment(@Param("courseNo") Long courseNo);

EnrollmentService.java

Course course = courseRepository.findAvailableByIdForEnrollment(request.courseNo()); if (course == null) { log.error("강의를 찾을 수 없거나 정원 초과: courseNo={}", request.courseNo()); throw new BusinessException(ErrorCode.COURSE_NOT_FOUND); // ❌ 애매한 에러! }

사용자가 받는 에러 메시지

❌ "강의를 찾을 수 없습니다"

사용자 입장:
- "강의 번호를 잘못 입력했나?"
- "강의가 삭제됐나?"
- "정원이 다 찬 건가?"
→ 실제 원인을 알 수 없어서 혼란스러움!

✅ AFTER (개선된 코드)

CourseRepository.java

@Lock(LockModeType.PESSIMISTIC_WRITE) @Query(""" SELECT c FROM Course c WHERE c.courseNo = :courseNo AND c.deleted = false """) // ✅ 정원 확인 제거, 존재 여부만 확인 Course findByIdForEnrollment(@Param("courseNo") Long courseNo);

EnrollmentService.java

Course course = courseRepository.findByIdForEnrollment(request.courseNo()); if (course == null) { log.error("강의를 찾을 수 없음: courseNo={}", request.courseNo()); throw new BusinessException(ErrorCode.COURSE_NOT_FOUND); // ✅ 명확: 없음 } // 정원 확인 (명확한 에러 메시지) if (!course.isAvailable()) { log.error("강의 정원 초과: courseNo={}, currentStudents={}, maxStudents={}", course.getCourseNo(), course.getCurrentStudents(), course.getMaxStudents()); throw new BusinessException(ErrorCode.COURSE_FULL); // ✅ 명확: 정원 초과 }

messages.properties

error.course.not.found=강의를 찾을 수 없습니다. // ✅ 강의가 없을 때 error.course.full=강의 정원이 가득 찼습니다. // ✅ 정원이 찼을 때

사용자가 받는 에러 메시지

강의가 없는 경우:
✅ "강의를 찾을 수 없습니다"
→ 강의 번호를 다시 확인하세요

정원이 찬 경우:
✅ "강의 정원이 가득 찼습니다"
→ 다른 분반을 선택하거나 대기하세요

→ 사용자가 정확한 원인을 알고 대처할 수 있음!

핵심 교훈

  • ✅ 계층별 책임 분리: Repository는 조회만, Service에서 비즈니스 검증
  • ✅ 명확한 에러 메시지: 사용자가 원인을 정확히 알 수 있어야 함
  • ✅ 에러 코드 분리: COURSE_NOT_FOUND vs COURSE_FULL
  • ✅ 로깅 상세화: currentStudents, maxStudents 함께 기록

개선 요약

1️⃣ currentStudents

  • ✅ 승인 시점에 증가
  • ✅ 취소 시 상태 확인
  • ✅ 비즈니스 로직 일치

2️⃣ 배치 트랜잭션

  • ✅ REQUIRES_NEW
  • ✅ 독립적 트랜잭션
  • ✅ 부분 성공 허용

3️⃣ 에러 메시지

  • ✅ 명확한 구분
  • ✅ 계층별 책임
  • ✅ 사용자 경험 개선

학습 포인트

이러한 안티패턴들은 초기에는 큰 문제로 보이지 않지만, 실제 서비스에서는 데이터 불일치, 사용자 혼란, 운영 어려움으로 이어집니다. 테스트를 통해 발견하고, 명확한 책임 분리와 에러 처리로 개선하는 것이 중요합니다.
