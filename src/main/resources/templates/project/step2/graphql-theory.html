GraphQL이란?

정의

GraphQL은 Facebook이 2015년 공개한 쿼리 언어이자 런타임입니다.

클라이언트가 필요한 데이터의 구조를 쿼리로 명시하면, 서버가 정확히 그 구조대로 응답하는 방식

GraphQL 동작 흐름

클라이언트

쿼리 작성

"이름과 강사만 주세요"

/graphql

스키마 확인

쿼리 해석 → DB 조회

응답

정확한 구조

요청한 필드만 반환

핵심 개념

  • 단일 엔드포인트: /graphql 하나로 모든 요청 처리
  • 클라이언트 주도: 필요한 필드만 선택 요청
  • 타입 시스템: 스키마로 API 구조 정의
  • Over-fetching 방지: 불필요한 데이터 전송 없음
  • Under-fetching 방지: 여러 API 호출 불필요

REST vs GraphQL

REST API

여러 엔드포인트:

GET /api/courses/1 GET /api/courses/1/curriculums GET /api/courses/1/students

고정된 응답 구조:

{ "courseNo": 1, "name": "JPA 마스터", "description": "...", "instructor": {...}, "maxStudents": 30, "status": "ACTIVE" // 클라이언트가 name만 필요해도 전부 전송 }

문제: Over-fetching & Under-fetching

GraphQL

단일 엔드포인트:

POST /graphql

클라이언트가 구조 지정:

query { course(id: 1) { name curriculums { title } students { name } } }

→ 요청한 필드만 응답

해결: 필요한 데이터만, 한 번에

상세 비교

항목 REST GraphQL
엔드포인트 여러 개 (리소스별) 하나 (/graphql)
데이터 요청 URL 경로 쿼리 작성
응답 구조 서버가 결정 (고정) 클라이언트가 결정
여러 리소스 여러 요청 필요 한 번에 조회
버전 관리 /api/v1, /api/v2 스키마 진화
캐싱 HTTP 캐싱 (쉬움) 커스텀 필요
학습 곡선 낮음 중간

GraphQL 핵심 개념

1 Schema (스키마)

API의 타입 시스템 정의 - "무엇을 조회할 수 있는가?"

type Course { courseNo: ID! name: String! description: String instructor: User! curriculums: [Curriculum!]! students: [User!]! maxStudents: Int! status: String! } type User { userNo: ID! name: String! email: String! } type Curriculum { curriculumNo: ID! weekNumber: Int! title: String! content: String }

2 Query (조회)

데이터 읽기 (REST의 GET에 해당)

type Query { # 단건 조회 course(id: ID!): Course user(id: ID!): User # 목록 조회 courses: [Course!]! users: [User!]! # 필터 조회 coursesByInstructor(instructorId: ID!): [Course!]! } # 사용 예시 query { course(id: 1) { name instructor { name } curriculums { title } } }

3 Mutation (변경)

데이터 생성/수정/삭제 (REST의 POST/PUT/DELETE에 해당)

type Mutation { # 생성 createCourse(input: CreateCourseInput!): Course! # 수정 updateCourse(id: ID!, input: UpdateCourseInput!): Course! # 삭제 deleteCourse(id: ID!): Boolean! # 비즈니스 로직 enrollCourse(courseId: ID!): Enrollment! } # 사용 예시 mutation { createCourse(input: { name: "Spring Boot 마스터" description: "Spring Boot 핵심" maxStudents: 30 }) { courseNo name } }

4 Resolver (리졸버)

쿼리/뮤테이션의 실제 구현 - "어떻게 데이터를 가져오는가?"

REST의 Controller 역할

@Component public class CourseResolver implements GraphQLQueryResolver { private final CourseService courseService; // Query 구현 public Course course(Long id) { return courseService.getCourse(id); } public List<Course> courses() { return courseService.getAllCourses(); } public List<Course> coursesByInstructor(Long instructorId) { return courseService.getCoursesByInstructor(instructorId); } } @Component public class CourseMutationResolver implements GraphQLMutationResolver { private final CourseService courseService; // Mutation 구현 public Course createCourse(CreateCourseInput input) { return courseService.createCourse(input); } public Course updateCourse(Long id, UpdateCourseInput input) { return courseService.updateCourse(id, input); } public Boolean deleteCourse(Long id) { courseService.deleteCourse(id); return true; } }

Step 3 Resolver 구현

@Component @RequiredArgsConstructor public class CourseQueryResolver implements GraphQLQueryResolver { private final CourseService courseService; public Course course(Long id) { return courseService.getCourse(id); } public List<Course> courses() { return courseService.getAllCourses(); } public List<Course> coursesByInstructor(Long instructorId) { return courseService.getCoursesByInstructor(instructorId); } } @Component @RequiredArgsConstructor public class CourseMutationResolver implements GraphQLMutationResolver { private final CourseService courseService; public Course createCourse(CreateCourseInput input) { return courseService.createCourse(input); } public Course updateCourse(Long id, UpdateCourseInput input) { return courseService.updateCourse(id, input); } public Boolean deleteCourse(Long id) { courseService.deleteCourse(id); return true; } }

주의: N+1 문제와 해결

문제 상황

query { courses { # 1번 쿼리 name instructor { # N번 쿼리 (각 Course마다) name } } }

Course가 10개면 총 11번 쿼리 실행 (1 + 10)

해결: DataLoader 사용

@Component public class UserDataLoader implements DataLoader<Long, User> { private final UserRepository userRepository; @Override public CompletableFuture<User> load(Long userId) { // 배치로 한 번에 조회 return CompletableFuture.supplyAsync(() -> userRepository.findById(userId).orElse(null) ); } @Override public CompletableFuture<List<User>> loadMany(List<Long> userIds) { return CompletableFuture.supplyAsync(() -> userRepository.findAllById(userIds) ); } }

✅ 여러 요청을 모아서 한 번에 조회 (배치 처리)

REST와 GraphQL 공존 전략

권장 전략

REST를 완전히 대체하지 말고, 병행 운영하는 것이 좋습니다.

  • REST: 간단한 CRUD, 공개 API, 캐싱 중요한 경우
  • GraphQL: 복잡한 데이터 조회, 모바일 앱, 프론트 주도 개발

우리 프로젝트 적용 예시

# REST (유지) GET /api/courses → 목록 (캐싱 활용) POST /api/courses → 생성 PUT /api/courses/{id} → 수정 DELETE /api/courses/{id} → 삭제 # GraphQL (추가) POST /graphql → 복잡한 조회 { courses { name instructor { name } curriculums { title } students { name } } }

GraphQL 장단점

장점

  • 필요한 데이터만 요청 (Over-fetching 방지)
  • 한 번에 여러 리소스 조회 (Under-fetching 방지)
  • 강력한 타입 시스템
  • 자동 문서화 (스키마 기반)
  • 프론트엔드 주도 개발
  • 버전 관리 불필요

단점

  • 학습 곡선 존재
  • 캐싱 복잡함 (HTTP 캐싱 불가)
  • N+1 문제 발생 가능
  • 파일 업로드 복잡
  • 쿼리 복잡도 제어 필요
  • REST보다 무거운 인프라

GraphQL이 적합한 경우

  • 모바일 앱: 네트워크 효율성 중요
  • 복잡한 데이터 관계: 여러 리소스 조회 필요
  • 프론트 주도: 프론트엔드가 데이터 구조 결정
  • 빠른 반복 개발: 백엔드 수정 최소화

결론 및 권장 사항

✅ 실무 가치: REST의 실질적인 대안, 실무 채택률 높음

🎯 학습 가치: HATEOAS보다 실용적, 현대적 API 설계 이해

⚡ 구현 난이도: 중간 (스키마 작성 + 리졸버 구현)
