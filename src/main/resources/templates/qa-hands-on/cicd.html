CI/CD가 뭔가요?

CI (Continuous Integration)

지속적 통합: 코드를 푸시할 때마다 자동으로 빌드 + 테스트

예시:

  1. 1. 개발자가 git push
  2. 2. GitHub Actions 자동 실행
  3. 3. ./gradlew test 자동 수행
  4. 4. 결과를 PR에 표시 (✅ 성공 / ❌ 실패)

CD (Continuous Deployment)

지속적 배포: 테스트 통과하면 자동으로 운영 서버에 배포

예시:

  1. 1. main 브랜치에 머지
  2. 2. 모든 테스트 자동 실행
  3. 3. 통과하면 Docker 이미지 빌드
  4. 4. AWS/Azure에 자동 배포 🚀

이번 실습: 7일 프로젝트에서는 CI (자동 테스트)만 구현해도 충분히 임팩트 있음! CD (자동 배포)는 시간이 남으면 도전해보세요.

GitHub Actions란?

GitHub에서 제공하는 무료 CI/CD 도구. 별도 설치 없이 .github/workflows/ 폴더에 YAML 파일만 추가하면 끝!

실습: GitHub Actions로 자동 테스트 설정

① 워크플로우 파일 생성

프로젝트 루트에 .github/workflows/test.yml 파일 생성: 

name: Run Tests

# 트리거: main/develop 브랜치에 push 또는 PR 생성 시
on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main, develop ]

jobs:
  test:
    runs-on: ubuntu-latest  # GitHub가 제공하는 우분투 서버

    steps:
    # 1단계: 코드 체크아웃
    - name: Checkout code
      uses: actions/checkout@v4

    # 2단계: Java 17 설치
    - name: Set up JDK 17
      uses: actions/setup-java@v4
      with:
        java-version: '17'
        distribution: 'temurin'

    # 3단계: Gradle 캐싱 (빌드 속도 향상)
    - name: Cache Gradle packages
      uses: actions/cache@v3
      with:
        path: |
          ~/.gradle/caches
          ~/.gradle/wrapper
        key: ${{ runner.os }}-gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}
        restore-keys: |
          ${{ runner.os }}-gradle-

    # 4단계: Gradle 권한 부여
    - name: Grant execute permission for gradlew
      run: chmod +x gradlew

    # 5단계: 테스트 실행
    - name: Run tests with Gradle
      run: ./gradlew test

    # 6단계: 테스트 결과 리포트 (실패 시에도 실행)
    - name: Publish Test Report
      uses: mikepenz/action-junit-report@v4
      if: always()  # 테스트 실패해도 리포트 생성
      with:
        report_paths: '**/build/test-results/test/TEST-*.xml'
        fail_on_failure: true

② GitHub에 푸시 

git add .github/workflows/test.yml
git commit -m "Add GitHub Actions CI workflow"

④ (선택) PR 보호 규칙 설정

테스트 통과해야만 머지 가능하도록 설정:

  1. 1. 저장소 → Settings 탭
  2. 2. 좌측 메뉴 → Branches
  3. 3. Add branch protection rule 클릭
  4. 4. Branch name pattern: main
  5. 5. ✅ Require status checks to pass before merging 체크
  6. 6. Status checks 검색에서 "test" 선택
  7. 7. Create 버튼 클릭

고급: 테스트 커버리지 자동 체크

테스트 커버리지: 전체 코드 중 몇 %가 테스트되었는지 측정
→ CI에서 자동으로 체크하여 "커버리지 60% 미만이면 머지 차단" 가능!

① build.gradle에 JaCoCo 추가 

plugins {
    id 'java'
    id 'org.springframework.boot' version '3.2.0'
    id 'io.spring.dependency-management' version '1.1.4'
    id 'jacoco'  // JaCoCo 플러그인 추가
}

// JaCoCo 설정
jacoco {
    toolVersion = "0.8.11"
}

// 커버리지 검증 태스크
jacocoTestCoverageVerification {
    violationRules {
        rule {
            limit {
                minimum = 0.60  // 최소 60% 커버리지
            }
        }
    }
}

// 테스트 후 커버리지 리포트 자동 생성
test {
    finalizedBy jacocoTestReport
}

// 커버리지 리포트 설정
jacocoTestReport {
    dependsOn test
    reports {
        xml.required = true
        html.required = true
    }
}

② test.yml 워크플로우 업데이트 

    # 5단계: 테스트 및 커버리지 실행
    - name: Run tests with coverage
      run: ./gradlew test jacocoTestReport jacocoTestCoverageVerification

    # 6단계: 커버리지 리포트를 PR 코멘트로 추가
    - name: Add coverage to PR
      if: github.event_name == 'pull_request'
      uses: madrapps/jacoco-report@v1.6.1
      with:
        paths: ${{ github.workspace }}/build/reports/jacoco/test/jacocoTestReport.xml
        token: ${{ secrets.GITHUB_TOKEN }}
        min-coverage-overall: 60
        title: 'Test Coverage Report'

이제 PR을 올리면 자동으로 커버리지가 코멘트로 달립니다!
60% 미만이면 워크플로우가 실패합니다 ❌

실무에서는 이렇게 씁니다

스타트업 / 소규모 팀

전략: 최소한의 설정으로 빠르게 시작

  • • GitHub Actions로 CI만 구현 (테스트 자동 실행)
  • • CD는 main 브랜치에 머지 후 수동 배포
  • • 커버리지 목표: 50% 이상
  • • 배포 주기: 주 1-2회 (금요일 피함)

중견 기업

전략: CI + 스테이징 자동 배포

  • • develop 브랜치 → 스테이징 서버 자동 배포
  • • main 브랜치 → 운영 서버는 승인 후 배포
  • • 커버리지 목표: 70% 이상
  • • Slack/Discord 알림 연동
  • • 배포 주기: 매일 (데일리 배포)

대기업

전략: 완전 자동화 + 다단계 배포

  • • Jenkins 또는 GitLab CI/CD (자체 호스팅)
  • • 테스트 → 스테이징 → 카나리 배포 → 운영 (단계별 자동)
  • • 커버리지 목표: 80% 이상 (강제)
  • • SonarQube 코드 품질 검사
  • • 성능 테스트 자동 실행 (JMeter/nGrinder)
  • • 배포 주기: 하루 여러 번 (Continuous Deployment)

면접에서 자주 나오는 질문

Q1: CI와 CD의 차이는?

A: CI는 코드 통합 시 자동으로 빌드와 테스트를 수행하는 것이고, CD는 테스트 통과 후 자동으로 배포까지 하는 것입니다. 저희 프로젝트에서는 CI를 먼저 구축했고, 시간이 허락하면 CD도 추가할 예정입니다.

Q2: GitHub Actions 말고 다른 도구도 있나요?

A: Jenkins가 가장 유명하고 대기업에서 많이 씁니다. GitLab CI/CD, CircleCI, Travis CI 등도 있습니다. GitHub Actions를 선택한 이유는 별도 설치 없이 즉시 사용 가능하고 무료이기 때문입니다.

Q3: 테스트가 너무 오래 걸리면 어떻게 하나요?

A: 단위 테스트와 통합 테스트를 분리해서, PR 시에는 단위 테스트만 빠르게 실행하고, main 머지 시에는 통합 테스트까지 전부 실행하는 전략을 쓸 수 있습니다. 또는 캐싱을 활용하거나 테스트를 병렬로 실행할 수도 있습니다.

Q4: 커버리지 목표는 얼마가 적당한가요?

A: 일반적으로 60-80%가 적당합니다. 100%를 목표로 하면 테스트 작성에 너무 많은 시간이 들어가고, 오히려 중요한 로직보다 단순 getter/setter 테스트에 집중하게 됩니다. 저희는 핵심 비즈니스 로직 위주로 70% 이상을 목표로 했습니다.

Pro Tips: CI/CD 고급 활용

Slack 알림 연동

테스트 실패 시 Slack 채널에 자동 알림 

- name: Slack Notification
  if: failure()
  uses: 8398a7/action-slack@v3
  with:
    status: ${{ job.status }}
    text: '테스트 실패! 확인 필요'
    webhook_url: ${{ secrets.SLACK_WEBHOOK }}

보안: Secrets 관리

API Key 같은 민감 정보는 Secrets에

  1. 1. 저장소 → Settings → Secrets → Actions
  2. 2. New repository secret 클릭
  3. 3. Name: DB_PASSWORD
  4. 4. YAML에서 사용: ${{ secrets.DB_PASSWORD }}

→ 로그에 절대 노출되지 않음 🔒
