1. Postman vs JUnit: 테스트 범위의 차이

구분 Postman JUnit
테스트 범위 Controller 계층만
API 엔드포인트 		전체 레이어
Entity, Service, Repository, Controller
실행 방법 수동 (클릭) 자동 (명령어 한 줄)
주요 목적 HTTP 요청/응답 검증 비즈니스 로직 + 통합 테스트
테스트 예시 POST /api/orders
상태 코드 200 확인 		Order.addItem()
양방향 관계 설정 검증

핵심 차이점

  • Postman: API가 외부에서 호출될 때 잘 동작하는지 확인 (Controller만)
  • JUnit: Entity 비즈니스 로직, Service 처리 과정, Repository 쿼리까지 모든 계층 검증
  • 둘 다 필요합니다. Postman으로 API를 확인하고, JUnit으로 내부 로직을 보장합니다.

4. 실습 1: 첫 단위 테스트 (5분)

실습 목표

Order 엔티티의 비즈니스 로직을 테스트합니다 (Service 아님!)

OrderTest.java

src/test/java/.../model/OrderTest.java 
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.DisplayName;
import static org.assertj.core.api.Assertions.*;

class OrderTest {

    @Test
    @DisplayName("주문에 아이템 추가 성공")
    void addItem_Success() {
        // given (준비)
        Order order = new Order("홍길동");
        OrderItem item = new OrderItem("노트북", 1, 1500000);

        // when (실행)
        order.addItem(item);

        // then (검증)
        assertThat(order.getItems()).hasSize(1);
        assertThat(item.getOrder()).isEqualTo(order);
    }

    @Test
    @DisplayName("총 금액 계산")
    void calculateTotalPrice() {
        // given
        Order order = new Order("홍길동");
        order.addItem(new OrderItem("노트북", 2, 1500000));
        order.addItem(new OrderItem("마우스", 1, 50000));

        // when
        BigDecimal total = order.getTotalPrice();

        // then
        assertThat(total).isEqualByComparingTo(new BigDecimal("3050000"));
    }

    @Test
    @DisplayName("주문 취소 시 상태 변경")
    void cancel_Success() {
        // given
        Order order = new Order("홍길동");
        order.setStatus(OrderStatus.PENDING);

        // when
        order.cancel();

        // then
        assertThat(order.getStatus()).isEqualTo(OrderStatus.CANCELLED);
    }
}

Given-When-Then 패턴

  • Given: 테스트 데이터 준비
  • When: 테스트할 동작 실행
  • Then: 결과 검증

5. 실습 2: MockMvc 통합 테스트 (10분)

실습 목표

실제 HTTP 요청처럼 Controller API를 테스트합니다

OrderApiTest.java

src/test/java/.../controller/OrderApiTest.java 
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest
@AutoConfigureMockMvc
@Transactional
class OrderApiTest {

    @Autowired
    private MockMvc mockMvc;

    @Autowired
    private ObjectMapper objectMapper;

    @Test
    @DisplayName("주문 생성 API 성공")
    void createOrder_Success() throws Exception {
        // given
        OrderRequest request = new OrderRequest("홍길동");

        // when & then
        mockMvc.perform(post("/api/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.id").exists())
            .andExpect(jsonPath("$.customerName").value("홍길동"))
            .andExpect(jsonPath("$.status").value("PENDING"));
    }

    @Test
    @DisplayName("주문 조회 API 성공")
    void getOrder_Success() throws Exception {
        // given: 주문 1개 미리 생성
        Long orderId = 1L;

        // when & then
        mockMvc.perform(get("/api/orders/{id}", orderId))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.id").value(orderId));
    }

    @Test
    @DisplayName("잘못된 요청 시 400 에러")
    void createOrder_Fail_BadRequest() throws Exception {
        // given: customerName 빈 값
        OrderRequest request = new OrderRequest("");

        // when & then
        mockMvc.perform(post("/api/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isBadRequest());
    }
}

MockMvc란?

실제 서버를 띄우지 않고도 HTTP 요청/응답을 테스트할 수 있는 도구입니다.
Postman처럼 동작하지만, 코드로 자동화된 버전!

7. 실무 Tip 💡

Tip 1 테스트 우선순위

1
Entity 비즈니스 로직 - 가장 중요!
2
핵심 API 2-3개 - 주요 기능만
3
복잡한 쿼리 - N+1 검증 등

Tip 2 @Transactional 활용

테스트 클래스에 붙이면 각 테스트 후 자동 롤백 

@SpringBootTest
@Transactional  // 이거 하나면 OK!
class OrderApiTest {
    // DB 상태 걱정 없음
}

Tip 4 Service는 테스트 안 해도 됨

8. GitHub Actions 연동 (보너스)

코드를 Push할 때마다 자동으로 테스트 실행하기

.github/workflows/test.yml

name: Test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
    - uses: actions/checkout@v2

    - name: Set up JDK 17
      uses: actions/setup-java@v2
      with:
        java-version: '17'

    - name: Run tests
      run: ./gradlew test
