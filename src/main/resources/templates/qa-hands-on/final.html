미션: 완벽한 주문 관리 시스템 QA

📋 시나리오

당신은 "스마트 쇼핑몰" 프로젝트의 QA 엔지니어입니다.
주문 관리 API가 완성되어 운영 배포 전 최종 품질 검증을 진행해야 합니다.

✅ 통과 조건:

  • • 모든 API 엔드포인트 정상 동작 확인 (Postman)
  • • 단위 테스트 커버리지 60% 이상 (JUnit)
  • • 성능 테스트 TPS 300 이상 달성 (nGrinder 또는 JMeter)
  • • CI/CD 파이프라인 구축 완료 (GitHub Actions)
  • • 최종 발표 자료 준비 (스크린샷 + 메트릭)

완료 시 얻는 것

  • • ✅ 대기업 수준의 QA 포트폴리오 완성
  • • ✅ 면접에서 바로 쓸 수 있는 실전 경험
  • • ✅ GitHub 프로필에 빛나는 초록불 (Actions 성공)
  • • ✅ 발표 시 "와, 전문가네" 소리 듣기 🎤

체크리스트: 단계별 미션

Lv.1

Mission 1: Postman Collection 구성

Pro Tip: Tests 탭에서 pm.test("Status code is 200") 추가하면 자동 검증!

Lv.2

Mission 2: JUnit 자동 테스트 작성

Pro Tip: Given-When-Then 패턴으로 작성하면 가독성 UP! 면접관이 좋아함.

Lv.3

Mission 3: 성능 테스트 (nGrinder 또는 JMeter)

Pro Tip: 7일 프로젝트면 nGrinder 추천! 포트폴리오면 둘 다 해보면 금상첨화.

Mission 4: GitHub Actions CI/CD 구축

Pro Tip: GitHub 프로필에 초록불이 가득하면 채용 담당자가 "열심히 하는 사람"이라고 인식!

Mission 5: 발표 자료 준비

Pro Tip: README가 잘 정리된 프로젝트는 GitHub Star 받기 쉬움! 포트폴리오 효과 2배.

최종 발표 완벽 대본 (3분 버전)

🎤 구조: 문제 → 과정 → 결과 → 배움

1️⃣ 문제 제기 (30초)

"안녕하세요. 저희는 스마트 쇼핑몰 프로젝트를 진행했습니다.
개발 초기에는 기능만 급하게 만들다 보니 테스트 없이 배포했고, 그 결과 운영 중에 주문이 누락되는 치명적인 버그가 발생했습니다.
이 경험을 통해 '품질 보증 프로세스'가 얼마나 중요한지 깨달았습니다."

2️⃣ 해결 과정 (90초)

[Postman] "먼저 Postman으로 모든 API 엔드포인트를 수동 테스트했습니다. 정상 케이스뿐 아니라 400, 404 등 에러 케이스까지 검증했고, Collection으로 저장했습니다."

[JUnit] "하지만 매번 수동 테스트는 비효율적이라 JUnit으로 자동 테스트를 작성했습니다. Entity 비즈니스 로직부터 API 통합 테스트까지 총 커버리지 70%를 달성했습니다."

[nGrinder/JMeter] "기능은 정상이지만 성능이 문제였습니다. nGrinder로 부하 테스트를 해보니 N+1 쿼리 문제로 TPS가 50에 불과했습니다. Fetch Join을 적용한 결과 TPS 500으로 10배 개선되었습니다."

[CI/CD] "마지막으로 GitHub Actions로 CI/CD를 구축했습니다. 이제 코드를 푸시하면 자동으로 모든 테스트가 실행되고, 실패하면 PR 머지가 차단됩니다. 팀원들의 실수를 사전에 방지할 수 있게 되었습니다."

3️⃣ 결과 (30초)

"결과적으로 다음과 같은 성과를 달성했습니다:"

  • ✅ 배포 후 버그 발생률 80% 감소
  • ✅ 테스트 커버리지 70% 달성 (자동 검증)
  • ✅ 성능 10배 향상 (TPS 50 → 500)
  • ✅ CI/CD 파이프라인 구축 (푸시 시 자동 테스트)

4️⃣ 배운 점 (30초)

"이 프로젝트를 통해 '테스트는 선택이 아닌 필수'라는 것을 배웠습니다.
처음에는 테스트 작성이 시간 낭비라고 생각했지만, 오히려 버그 수정 시간을 줄여 전체 개발 속도가 빨라졌습니다.
또한 대기업 수준의 QA 프로세스를 경험하면서 실무에서 바로 적용할 수 있는 자신감을 얻었습니다. 감사합니다."

발표 꿀팁

  • • 숫자를 강조하세요: "10배 향상", "80% 감소", "TPS 500" 같은 구체적 수치
  • • 화면을 보여주세요: 말만 하지 말고 실제 GitHub Actions 탭, 성능 그래프 띄우기
  • • 실패 경험을 먼저 말하세요: "처음엔 실패했지만 이렇게 해결했다"가 더 진정성 있음
  • • 3분 넘지 않기: 연습해서 정확히 2분 50초 맞추면 프로처럼 보임

예상 질문 & 모범 답변 (면접 대비)

Q1: 테스트 커버리지 70%인데, 나머지 30%는 왜 안 했나요?

모범 답변:

"100% 커버리지를 목표로 하면 단순 getter/setter까지 테스트하게 되어 비효율적입니다. 저희는 핵심 비즈니스 로직 우선 전략을 택했습니다. 예를 들어 Order 엔티티의 총액 계산 로직, 주문 생성 프로세스 등 버그 발생 시 치명적인 부분에 집중했습니다. 결과적으로 70% 커버리지로도 배포 후 버그가 80% 감소했습니다."

Q2: nGrinder와 JMeter 중 왜 nGrinder를 선택했나요?

모범 답변:

"7일 프로젝트라 시간이 제한적이었습니다. nGrinder는 Docker Compose 한 줄로 설치되고 웹 UI가 직관적이라 빠르게 시작할 수 있었습니다. JMeter는 설치부터 GUI 사용법 익히기까지 시간이 더 걸립니다. 다만 포트폴리오나 대기업 지원 시에는 JMeter HTML 리포트가 더 전문적으로 보이기 때문에, 시간이 허락한다면 둘 다 해보는 걸 추천합니다."

Q3: N+1 문제를 어떻게 발견했나요?

모범 답변:

"두 가지 방법으로 발견했습니다.
첫째, application.yml에서 spring.jpa.show-sql=true로 설정해서 실제 실행되는 쿼리를 로그로 확인했습니다. 주문 1개 조회인데 쿼리가 10개 이상 나가는 걸 보고 의심했습니다.
둘째, nGrinder로 부하 테스트를 돌렸을 때 TPS가 50에 불과했습니다. 평균 응답 시간도 2초나 걸렸고요. 이걸 보고 쿼리 최적화가 필요하다고 판단했습니다."

Q4: CI/CD 구축 후 실제로 도움이 됐나요?

모범 답변:

"네, 엄청 도움 됐습니다. 구체적인 사례를 들어드리면,
팀원 A가 급하게 기능을 추가하면서 기존 테스트를 깨뜨린 적이 있었습니다. CI/CD가 없었다면 그대로 배포되어 운영 장애가 났을 텐데, GitHub Actions가 자동으로 테스트를 돌리고 PR 머지를 차단해줬습니다.
또한 '내 로컬에서는 되는데?'라는 말이 사라졌습니다. 모든 테스트가 동일한 환경(GitHub 서버)에서 실행되니 환경 차이로 인한 문제가 없어졌습니다."

Q5: 실무에서도 이런 프로세스를 쓸 건가요?

모범 답변:

"네, 하지만 회사 규모에 맞게 조정할 것 같습니다.
스타트업이라면 Postman + JUnit + GitHub Actions CI만으로도 충분하고, 성능 테스트는 배포 전에만 한 번씩 할 것 같습니다.
중견 기업이라면 여기에 nGrinder를 추가해서 정기적으로 성능 체크하고, 스테이징 서버 자동 배포까지 구축할 것 같습니다.
대기업이라면 JMeter + Jenkins로 더욱 정교한 파이프라인을 만들고, SonarQube 같은 코드 품질 도구까지 연동할 것 같습니다.
중요한 건 도구보다 '테스트 자동화'의 철학을 이해하고 실천하는 것이라고 생각합니다."
