Dockerfile + Docker Compose 통합 이론

컨테이너 환경 구축의 핵심 개념을 한 번에 이해하기

개요 로컬 배포 AWS 배포
서버 준비 JAR 배포 Docker 이론 Dockerfile 배포 Compose 배포

🎯 핵심 개념

💡 둘 다 결국 "도커 컨테이너를 실행하기 위한 설정 파일"입니다!

하지만 목적이 다릅니다 - Dockerfile은 "개별 컨테이너 정의서", Compose는 "전체 시스템 구성도"

📝

Dockerfile

"하나의 앱을 이미지로 만드는 설계서"

개발자가 만든 애플리케이션을 도커 이미지로 변환
소스코드 → 이미지 → 컨테이너 변환 절차 정의
실행 명령: docker build
🎼

Docker Compose

"여러 이미지를 연결해서 완전한 서비스 환경을 구성하는 설계서"

앱 + DB + Redis + 기타 서비스를 한 번에 실행
서비스 간 연결, 의존관계, 네트워크 구성
실행 명령: docker compose up

💼 개발자 관점에서의 목적

구분 Dockerfile docker-compose.yml
역할 하나의 애플리케이션(컨테이너)을 이미지로 빌드하기 위한 설계서 여러 개의 컨테이너(DB, Redis, 앱 등)를 한 번에 실행/관리하기 위한 오케스트레이션 파일
대상 단위 단일 컨테이너 (예: app) 다중 컨테이너 (예: app, db, redis, mailhog 등)
파일 목적 애플리케이션의 이미지 생성 절차 정의 여러 이미지를 조합하여 서비스 전체 구성 정의
명령 실행 위치 docker build 명령으로 이미지 생성 docker compose up 명령으로 여러 컨테이너 실행
의존 관계 없음 (단일) 있음 (예: app → db → redis)
예시 파일 위치 프로젝트 루트에 Dockerfile 같은 위치 혹은 상위 폴더에 docker-compose.yml

🎯 결론 정리

🔹 Dockerfile

"하나의 앱을 이미지로 만드는 설계서"

🔹 docker-compose.yml

"여러 이미지를 연결해서 완전한 서비스 환경을 구성하는 설계서"

즉, Dockerfile은 "개별 컨테이너의 정의서", docker-compose는 "전체 시스템 구성도"라고 보면 됩니다.

💡 핵심 차이점

Dockerfile

  • • 개발자가 만든 앱을 이미지로 변환
  • • 단일 컨테이너만 관리
  • • 빌드 과정에 집중

Docker Compose

  • • 여러 서비스를 조합하여 실행

💻 실제 예시 (우리 프로젝트)

🎯 우리 JPA 프로젝트의 실제 파일들

아래는 현재 우리 프로젝트에 있는 실제 Dockerfile과 docker-compose.yml 파일입니다. 이 파일들을 보면서 Docker의 개념을 이해해보세요!

📝 우리 프로젝트의 Dockerfile

# Dockerfile (실제 파일)
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY build/libs/jpa-0.0.1-SNAPSHOT.jar app.jar
ENTRYPOINT ["java","-jar","app.jar"]
FROM eclipse-temurin:21-jre: Java 21 런타임 환경 사용
WORKDIR /app: 컨테이너 내 작업 디렉토리 설정
COPY build/libs/jpa-0.0.1-SNAPSHOT.jar app.jar: JAR 파일을 컨테이너로 복사
ENTRYPOINT: 컨테이너 실행 시 Java 애플리케이션 시작

👉 하나의 Spring Boot 앱 컨테이너를 만드는 레시피입니다!

🎼 우리 프로젝트의 docker-compose.yml

# docker-compose.yml (실제 파일)
version: "3.9"
services:
  app:
    build: .
    ports:
      - "8083:8082"
    container_name: jpa-app
    restart: unless-stopped
    networks:
      - appnet
    depends_on:
      - minio
  minio:
    image: minio/minio:latest
    container_name: jpa-minio
    restart: unless-stopped
    ports:
      - "9000:9000"
      - "9001:9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin123
    volumes:
      - minio_data:/data
    command: server /data --console-address ":9001"
    networks:
      - appnet

volumes:
  minio_data:

networks:
  appnet:
    external: true
version: "3.9": Docker Compose 파일 형식 버전
app 서비스: Spring Boot 애플리케이션 (포트 8083)
minio 서비스: S3 대용 파일 저장소 (포트 9000, 9001)
networks: appnet: 기존 appnet 네트워크 사용
depends_on: minio: 앱이 MinIO 시작 후 실행

👉 우리 앱을 실행하는 환경을 정의하는 오케스트라 지휘서입니다!

📋 Docker Compose 기본 문법

1️⃣ 기본 구조

version: "3.9"  # 고정 (최신 버전)
services:        # 서비스 정의 시작
  서비스명:
    # 서비스 설정들...
volumes:         # 볼륨 정의
networks:        # 네트워크 정의

2️⃣ 서비스 타입별 설정

📦 직접 빌드 (우리 앱)
build: . - Dockerfile 사용
🐳 이미지 사용 (DB, Redis 등)
image: redis:7-alpine - Docker Hub 이미지

3️⃣ 주요 설정 옵션

🏗️ 빌드 & 이미지
build: . - 현재 디렉토리 Dockerfile 사용
image: redis:7-alpine - Docker Hub 이미지
container_name: my-app - 컨테이너 이름
🌐 네트워크 & 포트
ports: ["8082:8082"] - 포트 매핑
networks: [appnet] - 네트워크 연결
depends_on: [db] - 의존성 설정
💾 데이터 & 환경
volumes: [db_data:/data] - 볼륨 마운트
environment: [KEY=value] - 환경변수
restart: unless-stopped - 재시작 정책
⚙️ 실행 & 명령
command: server /data - 실행 명령어
working_dir: /app - 작업 디렉토리
user: "1000:1000" - 사용자 지정

💡 핵심 포인트: version: "3.9"는 고정값이고, build: .는 우리 앱용, image: 이름는 외부 서비스용입니다!

🚀 실행 방법 (단계별 실습)

1️⃣ 단계: Docker만 사용 (개별 컨테이너)

먼저 Dockerfile만으로 우리 앱을 개별 컨테이너로 실행해봅시다.

💻 터미널 명령어 방식

# 1. JAR 파일 빌드 (소스코드 변경 시에만)
./gradlew build
# 2. Docker 이미지 빌드
docker build -t jpa-app .
# 3. 컨테이너 실행
docker run -p 8082:8082 jpa-app
💡 설명: JAR 파일이 이미 있으면 1단계 생략 가능

🔧 IntelliJ Docker 플러그인 방식

1. Docker 플러그인 설치: File → Settings → Plugins → "Docker" 검색 → 설치
2. Services 탭 열기: View → Tool Windows → Services
3. Dockerfile 연결: Docker 섹션에서 + 버튼 → Dockerfile 선택
4. 실행: Dockerfile에서 우클릭 → "Run" 선택
💡 장점: GUI로 쉽게 실행, 포트 매핑 자동 설정, 로그 확인 편함

✅ 1단계 완료 후 확인: http://localhost:8082에서 Spring Boot 앱이 실행되는지 확인하세요!

2️⃣ 단계: Docker Compose 사용 (다중 컨테이너)

이제 Docker Compose로 우리 앱과 MinIO를 함께 실행해봅시다.

💻 터미널 명령어 방식

# 1. 모든 서비스 실행 (앱 + MinIO)
docker-compose up --build
# 또는 백그라운드 실행
docker-compose up -d --build
💡 설명: --build 옵션으로 이미지 자동 재빌드, -d 옵션으로 백그라운드 실행

🔧 IntelliJ Docker Compose 방식

1. Run Configuration 생성: Run → Edit Configurations
2. Docker Compose 선택: + 버튼 → Docker Compose
3. 파일 경로 설정: Compose file: docker-compose.yml
4. 실행: Run 버튼 클릭
💡 장점: 여러 서비스 한 번에 관리, 의존성 자동 처리, 서비스별 로그 확인 가능

✅ 2단계 완료 후 확인:
• http://localhost:8083 - Spring Boot 앱
• http://localhost:9001 - MinIO 콘솔 (minioadmin/minioadmin123)

📁 프로젝트 디렉토리 구조

Docker 관련 파일들이 프로젝트 루트에 위치합니다: 

jpa/
├── Dockerfile              # 컨테이너 이미지 빌드 설정
├── docker-compose.yml      # 다중 컨테이너 실행 설정
├── .dockerignore           # Docker 빌드에서 제외할 파일들
├── build.gradle            # Gradle 빌드 설정
├── src/
│   └── main/
│       └── java/           # Spring Boot 소스코드
└── build/
    └── libs/
        └── jpa-0.0.1-SNAPSHOT.jar  # 빌드된 JAR 파일

📋 각 파일별 상세 설명

📝 Dockerfile

역할: Spring Boot 애플리케이션을 Docker 이미지로 변환하는 방법을 정의

주요 명령어:

  • • FROM eclipse-temurin:21-jre - Java 21 런타임 환경
  • • WORKDIR /app - 컨테이너 내 작업 디렉토리
  • • COPY build/libs/jpa-0.0.1-SNAPSHOT.jar app.jar - JAR 파일 복사
  • • ENTRYPOINT ["java","-jar","app.jar"] - 애플리케이션 실행

🎼 docker-compose.yml

역할: 여러 컨테이너(앱, MinIO)를 한 번에 실행하고 관리

주요 설정:

  • • app - Spring Boot 애플리케이션 (포트 8082)
  • • minio - S3 대용 파일 저장소 (포트 9000, 9001)
  • • networks: appnet - 기존 네트워크 사용
  • • depends_on - 서비스 간 의존관계 설정
  • • volumes - 데이터 영구 저장

🚫 .dockerignore

역할: Docker 빌드 시 불필요한 파일들을 제외하여 빌드 속도 향상 및 이미지 크기 최적화

제외되는 파일들:

  • • .gradle/, build/ - Gradle 빌드 파일 (JAR 제외)
  • • .idea/, .vscode/ - IDE 설정 파일
  • • *.log, logs/ - 로그 파일
  • • src/test/ - 테스트 코드
  • • README.md, docs/ - 문서 파일
  • • .git/ - Git 저장소 정보

💡 현재는 단순하지만...

지금은 앱 하나만 있지만, 실무에서는 보통 데이터베이스(MariaDB), 캐시(Redis), 웹서버(Nginx) 등도 함께 사용합니다. 그럴 때 docker-compose.yml에 더 많은 서비스들을 추가하게 됩니다!

🚀 실무 확장 예시 (우리 프로젝트 + 실무 서비스들)

실무에서 실제로 사용하는 유명한 서비스들을 추가한 확장 예시입니다: 

# 실무 확장된 docker-compose.yml 예시
version: "3.9"
services:
                  app:
                    build: .
                    ports:
                      - "8083:8082"
    container_name: jpa-app
    restart: unless-stopped
    networks:
      - appnet
    depends_on:
      - redis
      - minio
      - mailhog
      - jaeger
    environment:
      - SPRING_REDIS_HOST=redis
      - SPRING_REDIS_PORT=6379
      - SPRING_MAIL_HOST=mailhog
      - SPRING_MAIL_PORT=1025
      - MANAGEMENT_TRACING_ENABLED=true
      - MANAGEMENT_TRACING_JAEGER_ENDPOINT=http://jaeger:14268/api/traces

  # Redis - 캐시 및 세션 저장소
  redis:
    image: redis:7-alpine
    container_name: jpa-redis
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data

  # MinIO - S3 대용 파일 저장소
  minio:
    image: minio/minio:latest
    container_name: jpa-minio
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "9000:9000"
      - "9001:9001"
    environment:
      MINIO_ROOT_USER: minioadmin
      MINIO_ROOT_PASSWORD: minioadmin123
    volumes:
      - minio_data:/data
    command: server /data --console-address ":9001"

  # MailHog - 이메일 테스트 서버
  mailhog:
    image: mailhog/mailhog:latest
    container_name: jpa-mailhog
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "1025:1025"  # SMTP
      - "8025:8025"  # Web UI

  # Jaeger - 분산 추적 시스템
  jaeger:
    image: jaegertracing/all-in-one:latest
    container_name: jpa-jaeger
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "16686:16686"  # Web UI
      - "14268:14268"  # HTTP Collector
    environment:
      - COLLECTOR_OTLP_ENABLED=true

  # Prometheus - 메트릭 수집
  prometheus:
    image: prom/prometheus:latest
    container_name: jpa-prometheus
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus_data:/prometheus

  # Grafana - 모니터링 대시보드
  grafana:
    image: grafana/grafana:latest
    container_name: jpa-grafana
    restart: unless-stopped
    networks:
      - appnet
    ports:
      - "3000:3000"
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=admin123
    volumes:
      - grafana_data:/var/lib/grafana

volumes:
  redis_data:
  minio_data:
  prometheus_data:
  grafana_data:

networks:
  appnet:
    external: true

➕ 추가된 실무 서비스들

  • • Redis: 캐시 및 세션 저장소 (포트 6379)
  • • MinIO: S3 대용 파일 저장소 (포트 9000, 9001)
  • • MailHog: 이메일 테스트 서버 (포트 1025, 8025)
  • • Jaeger: 분산 추적 시스템 (포트 16686, 14268)
  • • Prometheus: 메트릭 수집 (포트 9090)
  • • Grafana: 모니터링 대시보드 (포트 3000)

🔗 실무 서비스 연결

  • • 네트워크: 기존 appnet 네트워크 사용
  • • 서비스명: redis, minio, mailhog, jaeger 등으로 접근
  • • 포트 매핑: 각 서비스별 고유 포트로 외부 접근
  • • 환경변수: Spring Boot에서 각 서비스 연결 정보 설정
  • • 데이터 영속성: Redis, MinIO, Prometheus, Grafana 데이터 유지

💼 실무 서비스 용도 설명

🔴 Redis

• 캐시: 자주 사용하는 데이터를 메모리에 저장

• 세션 저장: 로그인 상태, 장바구니 등

• 실시간 랭킹: 게임 점수, 조회수 등

📧 MailHog

• 이메일 테스트: 실제 이메일 발송 없이 테스트

• 개발 환경: 회원가입, 비밀번호 재설정 등

• 디버깅: 이메일 내용 확인 및 검증

📁 MinIO

• 파일 저장: 이미지, 문서, 동영상 등

• S3 호환: AWS S3와 동일한 API

• 로컬 개발: 클라우드 없이 파일 저장소 사용

🔍 Jaeger

• 분산 추적: 요청이 여러 서비스를 거치는 과정 추적

• 성능 분석: 어느 서비스에서 병목이 발생하는지 확인

• 디버깅: 복잡한 시스템에서 문제 원인 파악

📊 Prometheus

• 메트릭 수집: CPU, 메모리, 응답시간 등

• 모니터링: 시스템 상태 실시간 감시

• 알림: 문제 발생 시 자동 알림

📈 Grafana

• 대시보드: 모니터링 데이터를 시각화

• 차트: 성능 지표를 그래프로 표시

• 리포팅: 팀원들과 모니터링 정보 공유

⚡ 실제 실행 방법

우리 프로젝트를 Docker로 실행하는 실제 명령어들입니다:

1️⃣ Dockerfile로 실행

# 1. JAR 파일 빌드
./gradlew build

# 2. Docker 이미지 빌드
docker build -t jpa-app .

# 3. 컨테이너 실행
docker run -p 8082:8082 jpa-app

👉 하나의 컨테이너만 실행하는 방법

2️⃣ Docker Compose로 실행

# 1. JAR 파일 빌드
./gradlew build

# 2. 모든 서비스 실행
docker compose up -d

# 3. 서비스 상태 확인
docker compose ps

# 4. 서비스 중지
docker compose down

👉 여러 서비스를 한 번에 관리하는 방법

💡 핵심 메시지

"우리가 만든 Dockerfile로 애플리케이션 이미지를 만들었죠. 그런데 실무에서는 보통 DB, Redis 등도 같이 띄워야 하니까 — 그럴 때 쓰는 게 docker-compose입니다."

💼 실무 관점

언제 Dockerfile을 쓸까?

  • • 개발 단계: 애플리케이션 컨테이너 이미지 만들기
  • • 단순 배포: 하나의 서비스만 배포할 때
  • • CI/CD: 이미지 빌드 및 푸시
  • • 테스트: 단위 테스트용 컨테이너

언제 Compose를 쓸까?

  • • 로컬 개발: DB + Redis + 앱을 한 번에 띄우기
  • • 통합 테스트: 전체 시스템 환경 구성
  • • 스테이징: 프로덕션과 유사한 환경
  • • 데모: 빠른 환경 구축 및 시연

Dockerfile 고급 옵션

  • • .dockerignore: 불필요한 파일 제외 (필수!)
  • • Multi-stage build: 빌드 크기 최적화
  • • ARG vs ENV: 빌드 시 vs 런타임 변수
  • • HEALTHCHECK: 컨테이너 상태 모니터링
  • • USER: 보안을 위한 사용자 설정

Compose 고급 옵션

  • • Override files: 환경별 설정 분리
  • • Secrets: 민감한 정보 관리
  • • Profiles: 서비스 그룹 관리
  • • External networks: 기존 네트워크 활용
  • • Health checks: 서비스 의존성 관리
