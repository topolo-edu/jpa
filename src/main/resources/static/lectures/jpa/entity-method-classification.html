엔티티 메서드 분류 가이드

편의 메서드 / 비즈니스 메서드 / 헬퍼 메서드 구분과 운영 원칙

📌 핵심 원칙

  • 편의 메서드: 양방향 관계 동기화만 담당 (관계 설정 전용)
  • 비즈니스 메서드: 도메인 규칙, 상태 변경, 검증 로직
  • 헬퍼/쿼리 메서드: 탐색·필터링 (양방향 제거 시 Repository로 이동)

1️⃣ 편의 메서드 (Convenience Method)

목적

양방향 관계의 양쪽 엔티티를 동기화하는 것이 유일한 목적

특징

  • 관계 설정 시 양쪽 컬렉션/참조를 모두 업데이트
  • 연관관계 주인이 아닌 쪽에서 호출 권장
  • 비즈니스 로직 없음 (순수 관계 동기화만)
  • 양방향 관계가 없으면 존재 의미 없음

코드 예시

@Entity
public class Course {
    @OneToMany(mappedBy = "course", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Curriculum> curriculums = new ArrayList<>();

    // ✅ 편의 메서드: 양방향 동기화만
    public void addCurriculum(Curriculum curriculum) {
        this.curriculums.add(curriculum);
        curriculum.setCourse(this);  // 양방향 동기화
    }

    public void removeCurriculum(Curriculum curriculum) {
        this.curriculums.remove(curriculum);
        curriculum.setCourse(null);  // 양방향 동기화
    }
}

⚠️ 주의사항

양방향 관계를 제거하고 단방향으로 전환하면 편의 메서드는 삭제해야 합니다.

2️⃣ 비즈니스 메서드 (Business Method)

목적

도메인 규칙과 상태 변경 로직을 캡슐화

특징

  • 도메인 지식(비즈니스 규칙)을 표현
  • 상태 변경, 검증, 계산 로직 포함
  • 불변식(Invariant) 보장
  • 이름이 도메인 용어로 의미 명확 (activate, close, approve 등)

코드 예시

@Entity
public class Course {
    private Status status;
    private LocalDateTime activatedAt;

    // ✅ 비즈니스 메서드: 도메인 규칙 + 상태 변경
    public void activate() {
        if (this.status == Status.ACTIVE) {
            throw new IllegalStateException("이미 활성화된 강좌입니다");
        }
        this.status = Status.ACTIVE;
        this.activatedAt = LocalDateTime.now();
    }

    public void close() {
        if (this.status == Status.CLOSED) {
            throw new IllegalStateException("이미 종료된 강좌입니다");
        }
        this.status = Status.CLOSED;
    }
}

@Entity
public class Enrollment {
    private EnrollmentStatus status;

    public void approve() {
        if (this.status == EnrollmentStatus.APPROVED) {
            throw new IllegalStateException("이미 승인된 수강신청입니다");
        }
        this.status = EnrollmentStatus.APPROVED;
        this.approvedAt = LocalDateTime.now();
    }

    public void reject(String reason) {
        if (this.status == EnrollmentStatus.REJECTED) {
            throw new IllegalStateException("이미 거부된 수강신청입니다");
        }
        this.status = EnrollmentStatus.REJECTED;
        this.rejectionReason = reason;
    }
}

✅ 장점

  • • 도메인 로직이 엔티티에 응집
  • • 상태 변경 규칙이 한 곳에 집중
  • • 외부에서 setter로 임의 변경 불가

3️⃣ 탐색/조회 메서드 (Helper / Query / Finder Method)

목적

엔티티가 보유한 컬렉션을 필터링·탐색하여 필요한 데이터만 반환

특징

  • 읽기 전용 (상태 변경 없음)
  • 이미 로딩된 컬렉션만 필터링 (LAZY 강제 초기화 금지)
  • 양방향 관계 보유 시에만 의미 있음
  • 단방향 전환 시 Repository로 이동 필수

양방향 관계 보유 시

@Entity
public class User {
    @OneToMany(mappedBy = "student")
    private List<Enrollment> enrollments = new ArrayList<>();

    // ✅ 헬퍼 메서드: 메모리 필터링만 (DB 접근 없음)
    public List<Enrollment> getApprovedEnrollments() {
        return enrollments.stream()
            .filter(e -> e.getStatus() == EnrollmentStatus.APPROVED)
            .toList();
    }

    public int getApprovedCount() {
        return (int) enrollments.stream()
            .filter(e -> e.getStatus() == EnrollmentStatus.APPROVED)
            .count();
    }
}

양방향 제거 (단방향 전환) 시

// ❌ User 엔티티에 enrollments 컬렉션 없음 → 헬퍼 메서드 삭제
@Entity
public class User {
    // enrollments 컬렉션 없음
}

// ✅ Repository로 이동
public interface EnrollmentRepository extends JpaRepository<Enrollment, Long> {
    List<Enrollment> findByStudentAndStatus(User student, EnrollmentStatus status);

    @Query("SELECT e FROM Enrollment e WHERE e.student = :student AND e.status = :status")
    List<Enrollment> findByStudentIdAndStatus(@Param("student") User student,
                                                @Param("status") EnrollmentStatus status);
}

// Service에서 사용
@Service
public class EnrollmentService {
    public List<Enrollment> getApprovedEnrollments(User user) {
        return enrollmentRepository.findByStudentAndStatus(user, EnrollmentStatus.APPROVED);
    }
}

🚫 금지 사항

  • • 헬퍼 메서드 내에서 LAZY 컬렉션 강제 초기화 금지
  • • DB 쿼리 실행하는 로직 포함 금지
  • • 양방향 제거 후에도 엔티티에 남겨두기 금지

🎯 설계 원칙: CQRS 관점 (권장)

Command (명령)

상태 변경 = 엔티티/도메인 서비스

  • • 비즈니스 메서드
  • • 편의 메서드
  • • 트랜잭션 내에서 실행

Query (조회)

탐색/리스트 = Repository/쿼리 계층

  • • Repository Query Methods
  • • QueryDSL
  • • DTO/Projection

구현 예시

// ✅ Command: 엔티티 비즈니스 메서드
@Entity
public class Course {
    public void activate() {
        if (this.status == Status.ACTIVE) return;
        this.status = Status.ACTIVE;
        this.activatedAt = LocalDateTime.now();
    }
}

// ✅ Query: Repository
public interface EnrollmentRepository extends JpaRepository<Enrollment, Long>, EnrollmentQuery {
    List<Enrollment> findByStudentAndStatus(User student, EnrollmentStatus status);
}

// ✅ Query: QueryDSL
public class EnrollmentQueryImpl implements EnrollmentQuery {
    @Override
    public List<EnrollmentSimpleDto> findApprovedByStudent(Long studentId) {
        QEnrollment e = QEnrollment.enrollment;
        return queryFactory
            .select(Projections.constructor(EnrollmentSimpleDto.class,
                    e.enrollmentNo,
                    e.course.name))
            .from(e)
            .where(
                e.student.userNo.eq(studentId),
                e.status.eq(EnrollmentStatus.APPROVED),
                e.deleted.eq(false)
            )
            .fetch();
    }
}

✅ 운영 체크리스트

양방향 관계를 유지할 때

  • 편의 메서드로 양쪽 동기화 필수
  • 헬퍼 메서드는 메모리 필터링만 (DB 접근 금지)
  • 비즈니스 로직은 비즈니스 메서드에만

양방향을 단방향으로 전환할 때

  • 편의 메서드 전체 삭제
  • 헬퍼 메서드 → Repository Query Methods로 이동
  • 비즈니스 메서드는 그대로 유지

CQRS 원칙 적용 시

  • 상태 변경(Command) → 엔티티 비즈니스 메서드
  • 조회(Query) → Repository + QueryDSL + DTO
  • 헬퍼 메서드는 최소화하고 Repository 우선

📝 결론

편의 메서드: 양방향 동기화만 (관계 제거 시 삭제)

비즈니스 메서드: 도메인 규칙과 상태 변경 (항상 유지)

헬퍼 메서드: 메모리 필터링 (단방향 전환 시 Repository로 이동)

권장: CQRS 관점에서 Command(명령)는 엔티티에, Query(조회)는 Repository에 배치하여 책임을 명확히 분리합니다.
