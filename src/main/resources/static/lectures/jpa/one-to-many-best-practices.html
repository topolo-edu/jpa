💡 이 문서의 관점

JPA에는 @ManyToMany가 있지만, 이 강의에서는 다루지 않습니다.

이유:

  • 실무에서 거의 사용하지 않음 (중간 테이블에 추가 정보 필요한 경우가 대부분)
  • 나중에 리팩토링이 매우 고통스러움
  • 초보자에게 혼란만 가중

대신: 처음부터 중간 엔티티(Enrollment)를 만들어서 1:N + N:1로 설계하는 실무 방식을 학습합니다.

🚨 핵심 원칙

1. 단독 @OneToMany 단방향은 사용하지 마라

  • FK 위치와 연관관계 주인이 불일치 → 불필요한 UPDATE 쿼리 발생
  • 컬렉션(List) 관리 복잡 → NPE, FK 미설정 위험
  • 테이블 구조와 객체 구조 불일치 → 유지보수 어려움

→ 순수 1:N 관계라도 @ManyToOne 단방향 또는 양방향 사용

2. N:M 관계는 중간 엔티티로 1:N + N:1 구성

  • User ↔ Course 같은 N:M은 Enrollment 중간 엔티티로 분리
  • 추가 정보(상태, 일시, 금액) 저장 가능
  • 실무에서 거의 항상 이 방식 사용

❌ 왜 단독 @OneToMany는 문제인가?

문제 1: FK 위치 불일치 → 불필요한 UPDATE 쿼리

Team(1) → Member(N) 단방향 설정:

@Entity
public class Team {
    @OneToMany
    @JoinColumn(name = "team_id")  // Member 테이블의 FK
    private List<Member> members = new ArrayList<>();
}

실행 시 발생하는 SQL:

-- 1. Team 삽입
INSERT INTO team (name) VALUES ('개발팀');

-- 2. Member 삽입 (team_id는 null!)
INSERT INTO member (name, team_id) VALUES ('김철수', NULL);

-- 3. 불필요한 UPDATE 쿼리 발생!
UPDATE member SET team_id = 1 WHERE id = 1;

문제: FK는 Member 테이블에 있는데, 연관관계 주인은 Team이라서 JPA가 나중에 UPDATE로 FK를 채워야 함 (비효율!)

문제 2: 컬렉션(List) 관리의 함정

함정 A: 초기화 누락 → NPE

@OneToMany(mappedBy = "team")
private List<Member> members;  // null!

team.getMembers().add(member);  // ❌ NullPointerException!

// 해결: 필드 선언 시 초기화 필수
private List<Member> members = new ArrayList<>();

함정 B: add만 하면 FK 설정 안 됨

// 단방향에서:
team.getMembers().add(member);
entityManager.persist(team);

// DB 확인하면:
// member.team_id = NULL!  ← JPA가 자동으로 안 채워줌!

// 양방향이라도 편의 메서드 없으면 동일한 문제

문제 3: 테이블 구조와 불일치 → 직관성 저하

DB 구조:

member 테이블
├─ id
├─ name
└─ team_id (FK) ← Member가 Team 참조

JPA 구조:

Team 엔티티
└─ List<Member> members ← Team이 Member 참조

방향이 반대!

문제: DB는 "Member가 Team을 참조"하는데, 코드는 "Team이 Member를 소유"하는 구조 → 혼란!

✅ 권장: @ManyToOne 단방향

@Entity
public class Member {
    @ManyToOne
    @JoinColumn(name = "team_id")
    private Team team;  // Member가 Team 참조
}

// 사용:
member.setTeam(team);
entityManager.persist(member);

// SQL: INSERT member (team_id = 1)  ← 한 번에 끝!

장점: FK 위치와 일치, UPDATE 쿼리 없음, 직관적!

✅ N:M 관계의 올바른 해결 방법

🎯 핵심: N:M을 1:N + N:1로 구성

N:M 관계는 중간 엔티티를 만들어서 1:N + N:1 구조로 풀어야 합니다. 이렇게 하면 각 엔티티의 책임이 명확해지고, 추가 정보도 저장할 수 있습니다.

📚 우리 프로젝트 예시: 수강신청 시스템

User.java (단방향)

@Entity
public class User {
    @Id @GeneratedValue
    private Long userNo;

    private String name;
    private String email;

    // enrollments 컬렉션 없음 (단방향)
}

Enrollment.java (중간 엔티티)

@Entity
public class Enrollment {
    @Id @GeneratedValue
    private Long enrollmentNo;

    @ManyToOne  // ✅ User와의 N:1 관계
    @JoinColumn(name = "user_no")
    private User student;

    @ManyToOne  // ✅ Course와의 N:1 관계
    @JoinColumn(name = "course_no")
    private Course course;

    private EnrollmentStatus status;
    private LocalDateTime enrolledAt;
    private BigDecimal fee;

    // 비즈니스 메서드
    public void approve() {
        this.status = EnrollmentStatus.APPROVED;
        this.course.increaseCurrentStudents();
    }
}

Course.java (단방향)

@Entity
public class Course {
    @Id @GeneratedValue
    private Long courseNo;

    private String name;
    private String description;

    // enrollments 컬렉션 없음 (단방향)
}

결과: User 1:N Enrollment N:1 Course 구조로, 각 엔티티의 책임이 명확하고 추가 정보(신청일시, 승인상태, 수강료)도 저장 가능합니다.

🔍 Aggregate에 따른 양방향 선택

📌 핵심 원칙

Aggregate 내부 관계: 양방향 권장 (생명주기 관리)

Aggregate 간 관계: 단방향 기본 (Repository로 역방향 조회)

✅ Case 1: Aggregate 내부 관계

예시: Course ↔ Curriculum

특징:

  • Course가 Curriculum 생명주기 관리
  • Curriculum은 Course 없이 의미 없음
  • course.getCurriculums() 자주 사용

✅ 양방향 권장

@Entity
public class Course {
    @OneToMany(mappedBy = "course",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Curriculum> curriculums;

    // 편의 메서드로 정합성 보장
    public void addCurriculum(Curriculum c) {
        curriculums.add(c);
        c.setCourse(this);
    }
}

❓ Case 2: Aggregate 간 관계

예시: User ↔ Enrollment, Course ↔ Enrollment

특징:

  • User, Course, Enrollment 모두 독립적
  • 생명주기 독립 관리
  • 역방향 조회는 Repository로 가능

✅ 단방향으로 충분

@Entity
public class User {
    // enrollments 컬렉션 없음
}

// 필요할 때 Repository로 조회
@Service
public class EnrollmentService {
    public List<Enrollment> getMyEnrollments(User user) {
        return enrollmentRepository
            .findByStudent(user);
    }
}

⚡ 성능 비교

양방향:

// 1. User 조회
User user = userRepository.findById(1L);

// 2. Enrollment 조회
List<Enrollment> enrollments = user.getEnrollments();

// SQL:
// SELECT * FROM enrollment WHERE student_no = 1

단방향 + Repository:

// 1. User 조회
User user = userRepository.findById(1L);

// 2. Enrollment 조회
List<Enrollment> enrollments =
    enrollmentRepository.findByStudent(user);

// SQL:
// SELECT * FROM enrollment WHERE student_no = 1

💡 결론: SQL은 동일! 양방향이든 단방향이든 성능 차이 없음. 차이는 코드 결합도와 편의성뿐.

📚 우리 프로젝트의 선택과 이유

Course ↔ Curriculum: ✅ 양방향

  • Aggregate 내부 관계
  • Cascade로 생명주기 관리 필요
  • course.getCurriculums() 자주 사용 (커리큘럼 조회/수정)

User ↔ Enrollment: ❌ 단방향

  • Aggregate 간 관계 (독립적)
  • Repository로 조회하면 충분: enrollmentRepository.findByStudent(user)
  • 불필요한 결합도 제거로 코드 단순화

Course ↔ Enrollment: ❌ 단방향

  • Aggregate 간 관계 (독립적)
  • Repository로 조회하면 충분: enrollmentRepository.findByCourse(course)
  • Course 삭제 시 Enrollment 보존 가능 (이력 관리)

💡 학습 포인트:
• Aggregate 내부(Course ↔ Curriculum): 양방향 거의 필수
• Aggregate 간(User ↔ Enrollment): 단방향으로 충분, Repository 활용
• 프로젝트 특성에 맞게 선택하면 됨

📊 최종 정리

❌ 피해야 할 것

  • • 단독 @OneToMany 사용 (FK 위치 불일치, UPDATE 쿼리 문제)
  • • 불필요한 양방향 관계 설정 (Aggregate 간 관계)
  • • 복잡성만 증가시키는 설계

✅ 권장하는 것

  • • 기본은 @ManyToOne 단방향 사용
  • • N:M 관계는 중간 엔티티로 1:N + N:1 구성
  • • Aggregate 내부만 양방향 + Cascade 설정
  • • Aggregate 간은 단방향 + Repository로 조회

💡 핵심은 단순함과 명확성입니다. "필요할 것 같아서" 양방향을 설정하는 게 아니라, 실제로 사용하는지 확인 후 선택해야 합니다!
